# ナレッジベース構造テンプレート

このファイルは**構造の定義のみ**を持つ。事実（環境、案件、バージョン、URL）は一切書かない。
`CLAUDE.md` から `@import` しない（ロードしない層に属する）。
新しいリポジトリに適用するときは `/init-knowledge` がこのファイルを読んで骨格を作る。

---

## 0. 前提とするロード区分

Claude Code がファイルを読む経路は次の 4 区分しかない。

| 区分 | 経路 | コスト |
|---|---|---|
| (a) 常時ロード | `CLAUDE.md` / `CLAUDE.local.md`、その `@import` 先、`paths` なし rules | 毎セッション課金 |
| (b) パス条件ロード | `paths:` 付き rules。該当ファイルを読んだときだけ | 条件付き |
| (c) 呼び出し時ロード | スキル本文、スキルの参照ファイル、指示されて Read / 全文検索した結果 | 使ったときだけ |
| (d) ロードしない | 上記以外の全ファイル | 0 |

付随する前提：

- Claude は Markdown 内のリンクを**自動では辿らない**。関連ファイルは指示形（「〇〇のときは `<相対パス>` を Read する」）で書く。
- `CLAUDE.md` は 200 行未満が公式推奨。`@import` は分割の手段であり、コンテキスト削減にはならない。
- 同じ事実が 2 か所にあって食い違うと、Claude はどちらかを恣意的に選ぶ。

## 1. 採用した手法と、それぞれが担う次元

| 手法 | 判定 | 担う次元 |
|---|---|---|
| メダリオンアーキテクチャ | 採用 | **層**：何をロードするか、原本不変 |
| PARA | 採用 | **Silver 内の分類**：ロード頻度の勾配 |
| Johnny.Decimal | 部分採用 | **トップレベルの命名**：パス固定、共通スクリプト |
| Zettelkasten | 部分採用 | **1 ファイルの書き方**：原子性のみ |

4 つとも使うが、それぞれ担う次元が違うため衝突しない。
Zettelkasten は中核機能（リンク追跡）を捨てており、実質「原子性の原則」だけを借用している。
理由：Claude はリンクを辿らないため、リンクグラフはロード区分に写像できない。

## 2. ディレクトリ構造

### 2-1. ユーザー側（全リポジトリに効く。振る舞いのみ、事実は置かない）

```
<ユーザー設定ディレクトリ>/
  CLAUDE.md                        (a) 全repo常時   行動規則のみ・40行以内
  rules/
    <言語・ツール>.md              (b) 条件         paths: で対象を限定する
  hooks/
    protect-bronze.ps1 / .sh       PreToolUse  (Edit|Write)
    post-edit-check.ps1 / .sh      PostToolUse (Edit|Write)
  skills/                          全repoで使える構造操作スキル
    init-knowledge/SKILL.md        新しい repo に骨格を作る
    update-facts/SKILL.md          事実を 10-silver に追記する
    archive-work/SKILL.md          作業単位を work から archive へ移す
  templates/
    knowledge-design.md            このファイル。(d) ロードしない
  settings.json                    env / defaultShell / hooks
```

ユーザー側に置いてよいもの＝**リポジトリを問わず同じである振る舞い**。
ユーザー側に置いてはいけないもの＝**リポジトリごとに違う事実**。

### 2-2. プロジェクト側（リポジトリごと。すべて同じ形にする）

```
<repo>/
  CLAUDE.md                        (a) この repo で常時   概要 + @import 行
  .gitignore
  .claude/
    rules/                         (b) 条件   この repo 固有のバージョン依存規則
    skills/                        (c)        この repo 専用のエージェント
  knowledge/
    00-system/
      design-notes.md              (d) この repo 固有の設計調整点
      scripts/                     (d) エージェント起動層
    10-silver/                     Claude が読む唯一の層
      areas/*.md                   (a) 常時        終わりのない責任領域
      work/index.md                (a) 常時        進行中の作業単位・1件1行
      work/<id>.md                 (c) 呼び出し時   作業単位の詳細
      resources/*.md               (c) 呼び出し時   参照資料の要約
      archive/*.md                 (d)             終了した作業単位
    20-bronze/                     (d)             原本・不変
    30-gold/                       (d)             成果物・エージェント出力
```

## 3. 命名規則

- トップレベルの層にのみ 2 桁プレフィックスを付ける：`00-` `10-` `20-` `30-`。
  それ以下の階層には番号を付けない。番号の価値はソート安定性とパス固定であり、
  それはトップレベルだけで得られる。深い採番は手維持コストを壊す。
- 番号順は「読む頻度の高い層が若い番号」。メダリオンの処理の流れ順ではない。
- 作業単位の ID はケバブケース。ファイル名 `<id>.md`、`index.md` の行と同じ ID を使う。
- Bronze と Gold の日付ディレクトリは `yyyy-MM-dd` 固定。

## 4. 層の責務

| 層 | 誰が書くか | 誰が読むか | 不変か |
|---|---|---|---|
| `00-system/` | 人間 | 人間・スクリプト | 可変 |
| `10-silver/` | 人間・Claude（スキル経由） | **Claude が読む唯一の層** | 可変 |
| `20-bronze/` | **スクリプトのみ** | 誰も読まない（人間が遡るときだけ） | **不変・追記のみ** |
| `30-gold/` | スクリプト・エージェント | 人間 | 可変 |

`10-silver/` の各ファイルは：

- 断定文で書く。
- 1 ファイル = 1 トピック。同じ事実を 2 か所に書かない。
- コードから導出できる情報（ディレクトリ構成、依存一覧）は書かない。
- 関連ファイルは指示形で参照させる（リンクは辿られない）。

## 5. 常時ロード予算

| 対象 | 上限 |
|---|---|
| ユーザー `CLAUDE.md` | 40 行 |
| `paths` なし rules | 0 行（rules は必ず `paths:` を付ける） |
| プロジェクト `CLAUDE.md` | 30 行 |
| `areas/*.md` | **2 ファイルまで、各 50 行以内** |
| `work/index.md` | 10 行 |
| **合計** | **250 行を上限とする** |

超えたら §6 の降格規則を適用する。

## 6. 昇格・降格・状態遷移

### 作業単位の状態遷移

```
新規   → work/index.md に 1 行追加 + work/<id>.md を作成
進行中 → 詳細は work/<id>.md に書く
終了   → /archive-work <id>
         ① work/<id>.md を archive/<id>.md へ移動
         ② work/index.md から該当行を削除
```

### 昇格規則（Areas と Projects の境界を機械的に決める）

`work/<id>.md` に書いた事実のうち、**その作業単位が終わっても真であり続けるもの**だけを
`areas/` に移す。移したら `work` 側からは消す。これで同じ事実が 2 か所に残らない。

### 降格規則

| 移動 | 条件 |
|---|---|
| `areas/` → `resources/` | 常時ロード合計が予算超過 / その事実が 30 日参照されなかった |
| `work/<id>.md` → `archive/` | 完了 / 90 日停滞 |
| `resources/` → `archive/` | 参照元の `areas/` 記述が消えた |
| Bronze・Gold | 移動しない。削除は人間が明示的に行う |

## 7. 事実ファイルの更新手順

```
新しい事実が判明
  → /update-facts <事実>
  → 10-silver/ を全文検索し、矛盾する既存行を探す
  → 矛盾あり : 削除案を提示 → 承認を待つ → 書き換え
  → 矛盾なし : 適切な areas/ または work/<id>.md に追記
  → areas/ が行数上限を超えたら resources/ への分割を提案
```

`20-bronze/` には決して書かない。

## 8. 原本不変を守る手段と、その限界

| 層 | 手段 | 効く相手 |
|---|---|---|
| 1 | `protect-bronze`（PreToolUse, Edit\|Write）でパスに `/knowledge/20-bronze/` を含むなら拒否 | Claude の Edit / Write |
| 2 | ユーザー `CLAUDE.md` の行動規則「`20-bronze/` は読まない・書かない」 | Claude の判断 |
| 3 | 構造操作スキル本文に「20-bronze には書かない」と明記 | スキル実行時 |
| 4 | Bronze への書き込みは収集スクリプトのみ。追記であって書き換えない | スクリプト |

**限界（設計上の既知の穴）**：hook の matcher は `Edit|Write` なので、
シェル経由の書き込み（`Set-Content` 等）は素通りする。収集スクリプトが Bronze に書けるのは
まさにこの経路だからであり、同じ経路で Claude も書けてしまう。
塞ぐには `Bash` / `PowerShell` matcher にコマンド文字列検査を足す必要があるが、
誤検知でシェルが止まるリスクが増えるため、この設計では塞がず限界として記録する。

## 9. 新しいリポジトリへの適用手順

```
cd <新しい repo>
/init-knowledge
```

`/init-knowledge` が行うこと：

1. このテンプレートの §2-2 のツリーを作る（空ファイルと見出しのみ）。
2. `20-bronze/` と `30-gold/` を `.gitignore` に追加する。
3. 既存の `CLAUDE.md` があれば残し、末尾に `@import` 行だけ追記する。
   無ければ `/init` 相当の内容を生成して人間に見せ、承認後に `@import` 行を加える。
4. `areas/` は空の見出しだけを作る。**事実は書かない**。人間に質問して埋める。

## 10. 仕様の確認手順

Claude Code の仕様（hooks の JSON スキーマ、rules のフロントマターキー、permission の書式、
headless のフラグ）はバージョンで変わる。このテンプレートには**確認結果を書かない**。
使う直前に実測で確認し、結果はそのリポジトリの `10-silver/resources/` に
バージョンを明記して記録する。

確認手段（優先順）：

1. `claude --help` および `claude <subcommand> --help`
2. `claude` 実行ファイル内に埋め込まれたスキーマ定義・ドキュメント文字列の抽出
3. 捨て hook を仕込んで stdin JSON を実際にダンプする（hook 設定の反映にはセッション再起動が要る）
4. 公式リファレンス（管理設定で `WebFetch` が deny されている環境では使えない）

## 11. この設計への反対仮説（定期的に再検証する）

1. **メダリオンの 3 層は個人 repo には過剰で、Bronze と Gold は空のまま腐る。**
   成立条件：無人エージェントを回さない、または出力を読み返さない場合。
   検証：30 日運用して `20-bronze/` を一度も参照しなかったら Bronze を廃止する。

2. **`areas/` の常時ロードは不要で、常時ロードは 0 行でよい。**
   成立条件：「不明点は `knowledge/` を検索してから質問する」規則が確実に守られる場合。
   反論：規則が守られる保証がなく、破られたときの失敗は静かで検出しにくい。
   検証：`areas/` を空にして 1 週間運用し、誤った前提で作業した回数を数える。

3. **1 人 repo では PARA の Areas / Projects 分離は過剰。**
   成立条件：同時進行の案件が 2 件以下で、各案件が 2 週間以内に終わる場合。
   検証：`work/index.md` が 3 週間 1〜2 行のままなら 1 枚に統合する。

4. **ユーザー側に hooks を置くと、`knowledge/` を持たない repo で純粋なオーバーヘッドになる。**
   成立条件：実際に `knowledge/` を作る repo が 1〜2 個にとどまる場合。
   トレードオフ：各 repo 側に置けば無駄は消えるが、「全 repo で同じ設定」が成立しなくなる。
   検証：`knowledge/` を持つ repo が 3 個を超えなければ、プロジェクト側への移動を検討する。
